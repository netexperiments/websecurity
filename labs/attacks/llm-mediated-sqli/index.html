    LLM-mediated SQL Injection

    Flow: natural-language prompt → LLM → generated SQL → backend execution → database change → confirmation

    Objective

    Improper output handling is a vulnerability in LLM applications that occurs when responses generated by the model are missing filtration and sanitization. This is especially dangerous when that output flows into another interpreter. Hackergram's /leaderboard endpoint lets a user ask a leaderboard question in plain English, and answers it by having an LLM translate that question into a SQL query which the backend then executes directly. This experiment demonstrates that the generated SQL is trusted and run without validation, so a crafted natural-language prompt can make the LLM emit (and the backend execute) a SQL statement that changes another user's password, entirely through the chat-like interface.

    Affected Hackergram functionality

    • /leaderboard: natural-language leaderboard queries. (/generate_post is the other LLM-facing endpoint in Hackergram; see LLM-mediated Stored XSS, Indirect Prompt Injection, and System Prompt Leakage for the attacks that target it.)

    Prerequisites

    Full deployment with the llama2 model pulled in Ollama (see LLM Setup). No attacker HTTP server or proxy is needed, because the entire attack happens through the /leaderboard chat input.

    Initial state

    Run /reset first, then log in as any non-admin user.

    Vulnerable implementation

    The root cause of LLM-mediated SQL injection is that model output flows directly into a database interpreter without any structural validation. A representative vulnerable pattern in Hackergram:

    query = llm.generate(f"Write SQL to find user {username}")
db.execute(query)

    If the model outputs a destructive statement such as DELETE FROM users, the database executes it with full server privileges. There is no allowlist of permitted statement types (e.g. SELECT-only), no parameter binding, and no review step between "LLM produced this SQL" and "the database ran it."

    Experiment

    Walk through the full chain (prompt → LLM → generated SQL → backend → database) step by step:

    1. Intended natural-language functionality. Experiment with the functionality by submitting a normal prompt, such as "Give me the count of leaderboard members." Observe how the prompt generates a query to the application's database.
    2. Crafted prompt. Next, try to find a way to change another user's password through the endpoint.
    3. Generated SQL → backend execution. If you succeed, you should see the SQL query that was executed.
    4. Confirmation. To confirm the success of the attack, log out of your current account and log in to the affected account.

    Additional exercise

    Drop a table from the Hackergram database.

    Expected result

    You're able to log in as the targeted user using the password your prompt caused the LLM to set. This proves that the full chain from natural-language input to an unauthorized database write actually executed.

    LLM output is probabilistic

    The exact prompt wording that succeeds, and the exact SQL the model generates, can vary between runs and between model versions. If a given phrasing doesn't work, try rephrasing rather than expecting one specific wording to reproduce identically every time.

    Why it works

    The /leaderboard feature was built on the assumption that the LLM only ever generates read-only, leaderboard-shaped queries. Nothing in the backend actually enforces that assumption: the generated SQL is executed with the same lack of validation as any other unparameterized query in Hackergram (see SQL Injection). The LLM becomes an attacker-steerable SQL generator sitting in front of a database that trusts whatever it's handed. This is an instance of an output-to-interpreter violation: the model acts as an untrusted code generator whose output flows directly into another interpreter (a SQL engine here, the browser's HTML renderer in LLM-mediated Stored XSS) without structural validation in between.

    Reset / cleanup

    Run /reset to restore all user passwords and leaderboard state.

    Inspect and modify

    Preventing this requires constraining the model's output to a predefined structure and ensuring that only parameterized queries or allowlisted operations are permitted. The model should express intent, not executable SQL. Require the model to produce structured data and map that to a safe, parameterized query:

    Secure LLM SQL Interaction 
    import json

command = llm.generate(user_prompt)
parsed = json.loads(command)

if parsed.get("action") not in ["search", "summarize"]:
    abort(400)

# Map the parsed intent to a safe parameterized query
if parsed["action"] == "search":
    cursor.execute("SELECT * FROM users WHERE username = %s", (parsed["target"],))

    This approach prevents the model from generating arbitrary SQL. The application enforces an allowlist of permissible actions, and all values from model output are passed as bound parameters rather than interpolated into query text. Apply this to /leaderboard, repeat the attack, and confirm the crafted prompt no longer results in a password change.

    Exercise

    Using the same technique, drop a table from the Hackergram database via a crafted /leaderboard prompt.

    Hint

    💡 Hint Ask the model directly for the SQL it would run for a given request before asking it to also execute something destructive. Seeing the generated statement first makes it much easier to steer toward a `DROP TABLE` rather than guessing blind.
