# LLM-mediated Stored XSS

**Flow:** `stored attacker content → LLM summarization → generated HTML → persistent storage/rendering → browser execution`

## Objective

Improper output handling is a vulnerability in LLM applications that occurs when responses generated by the
model are missing filtration and sanitization. This is especially dangerous in web applications where outputs can be
dynamically inserted into the DOM. Hackergram's `/ai_summarize` feature asks an LLM to produce an HTML summary
of a post's content. This experiment demonstrates that the model's HTML output is inserted into the page
without sanitization, so a post can instruct the LLM (via its own text) to include an XSS payload in the
summary it generates.

## Affected Hackergram functionality

- `/ai_summarize`: AI-generated post summaries.

## Prerequisites

Full deployment with the `mistral` model pulled in Ollama (see [LLM Setup](../../llm-setup.md)). No attacker HTTP server needed; the payload is delivered as
ordinary post content.

## Initial state

Run `/reset` first, then log in as any user.

## Vulnerable implementation

The root cause is that model-generated markup is stored and later rendered without sanitization. A
representative vulnerable pattern:

```python
html = llm.generate(f"Write a summary for this post: {post_content}")
store_in_database(html)
```

If the model produces a payload such as `<script>stealCookies()</script>`, the application stores and later
serves it as executable markup: `/ai_summarize` inserts the LLM's HTML output directly into the page with no
sanitization pass such as `bleach.clean()`.

## Expected result

Viewing the AI-generated summary of the post triggers a JavaScript alert — the model's HTML output included
the attacker's `<img onerror=...>` tag, and the browser executed it as part of rendering the summary.

!!! note "LLM output is probabilistic"
    Whether and how the model follows an embedded instruction like this can vary between runs and between
    model versions. If the exact payload above doesn't trigger the alert, try adjusting the phrasing or
    hiding technique — the underlying vulnerability (unsanitized HTML output) doesn't depend on one specific
    prompt succeeding.

## Why it works

This is an instance of an **output-to-interpreter violation**: the model acts as an untrusted markup
generator whose output flows into the browser's HTML interpreter, exactly the same class of failure as
[LLM-mediated SQL Injection](llm-mediated-sqli.md) (SQL engine instead of HTML renderer). Because the model is
summarizing attacker-controlled post content, and that content can contain instructions the model follows
(an *indirect* form of prompt injection — see [Indirect Prompt Injection](indirect-prompt-injection.md)), the
attacker effectively gets to choose part of the HTML the application renders, without ever submitting a
`<script>` tag through a form field that might be sanitized directly.

## Reset / cleanup

Run `/reset` to remove the malicious post and any cached summary.

## Inspect and modify

All model-generated content must be treated as untrusted and sanitized before storage or rendering. Apply an
HTML sanitizer to strip executable markup before the content is stored:

```python
import bleach

ALLOWED_TAGS = ["p", "b", "i", "em", "strong", "ul", "ol", "li", "br"]
ALLOWED_ATTRS = {}

html = llm.generate(f"Write a profile bio for {username}")
safe_html = bleach.clean(html, tags=ALLOWED_TAGS, attributes=ALLOWED_ATTRS, strip=True)
store_in_database(safe_html)
```

Where appropriate, a general defense is to require the model to produce structured data rather than free-form
HTML, and then render that data through safe templates — constraining model output to a predefined schema and
enforcing an allowlist of permissible actions prevents the model from generating arbitrary HTML payloads.
Apply the sanitizer to `/ai_summarize`, repeat the attack, and confirm the `onerror` handler is stripped or
neutralized.
